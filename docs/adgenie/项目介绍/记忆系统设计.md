# AdGenie 记忆系统设计

## 目标

AdGenie 的记忆系统从 `MEMORY.md` 自由文本追加升级为分层结构化记忆。核心目标是：

- 新开对话时仍能继承稳定偏好、角色资产和成功模板
- 长对话不再依赖完整历史塞入上下文
- Agent 内部使用可检索、可去重、可标记置信度的结构化记录
- `MEMORY.md` 保留为用户可读镜像，而不是内部数据库

## 分层设计

### Tier 0 — 身份/配置层

人工维护，不属于自动学习记忆：

- `AGENTS.md`：行为规则、禁止操作、快捷指令
- `TOOLS.md`：本地工具配置、模型偏好、服务地址
- `IDENTITY.md`：Agent 身份
- `USER.md`：人工填写的用户画像
- `SOUL.md`：沟通风格和人格设定

这些文件仍由 `workspace_service.get_workspace_context()` 读取，并按原规则注入 System Prompt。`MEMORY.md` 不再全量注入。

### Tier 1 — 结构化长期记忆

真实数据源：

```text
backend/storage/memory.sqlite3
```

核心表：`memory_records`。

记录字段包括：

```json
{
  "id": "mem_xxx",
  "type": "角色资产 | prompt模板 | 用户偏好",
  "content": "用户偏好写实、电商商业质感，避免卡通二次元。",
  "summary": "用于 prompt 注入的短摘要",
  "scope_type": "global | user | canvas | brand | character",
  "scope_id": "default_user",
  "confidence": "confirmed | inferred | rejected | deprecated",
  "source_session_id": "canvas_xxx",
  "created_at": "...",
  "updated_at": "...",
  "use_count": 3,
  "embedding_json": "[...]",
  "metadata_json": "{}"
}
```

`write_memory` 工具现在写入 `memory_records`，并把 `confidence` 标记为 `confirmed`。写入后会刷新 `workspace/MEMORY.md` 镜像。

### Tier 2 — 会话摘要层

核心表：`session_digests`。

每个 canvas 维护一条滚动摘要：

- 当前任务类型
- 最近用户需求
- 本轮输出结果
- 工具生成的最终产物路径
- 用户满意度的轻量判断

这层用于上下文压缩，也用于后续从会话中提取 `inferred` 候选记忆。

### Tier 3 — 按需检索注入

Agent 创建时使用当前用户消息作为检索 query：

```text
当前 user message
  -> 本地 embedding
  -> memory_records cosine 相似度检索
  -> 加权排序
  -> 注入 Top K 相关记忆
```

当前实现不依赖外部向量数据库，也不需要 Milvus/Qdrant/FAISS。`memory_service.embed_text()` 使用本地确定性 hashing embedding，SQLite 存储向量 JSON，小规模记忆量足够使用。

排序会考虑：

- 相似度
- `confirmed` 置信度加分
- 同 canvas/scope 加分
- 使用次数加分
- `rejected` / `deprecated` 排除

注入格式示例：

```text
<session_digest>
任务类型：image
满意度：unknown
摘要：用户正在制作耳机商品图，偏好写实商业质感。
</session_digest>

<relevant_memory>
- [confirmed][用户偏好] 用户偏好写实、电商商业质感，避免卡通二次元。
- [inferred][用户偏好] 用户要求视频控制在 5 秒以内。
</relevant_memory>
```

## 运行链路

```text
服务启动
  -> workspace_service.ensure_workspace_defaults()
  -> memory_service.init_memory_store()
  -> 首次迁移旧 MEMORY.md 到 SQLite

用户发送消息
  -> agent_service.create_agent(current_query, canvas_id)
  -> workspace_service.get_workspace_context(query, canvas_id)
  -> Tier 0 文件注入 + Tier 1/2 检索注入
  -> LangGraph Agent 推理

流式响应结束
  -> history_service.save_canvas()
  -> memory_service.upsert_session_digest()
  -> memory_service.extract_inferred_memories_from_turn()
  -> 必要时刷新 MEMORY.md 镜像
```

## 写入策略

`confirmed` 记忆：

- 由 Agent 调用 `write_memory` 写入
- 用户明确表达满意、喜欢、以后默认使用、Prompt 效果好时触发

`inferred` 记忆：

- 每轮对话结束后由 `extract_inferred_memories_from_turn()` 轻量抽取
- 只做保守启发式提取
- 与 confirmed 分开，检索时权重更低

不会长期保存：

- 普通闲聊
- 一次性任务参数
- 临时工具路径本身
- 未确认的随机生成内容

## MEMORY.md 的新角色

`workspace/MEMORY.md` 现在是结构化记忆的可读镜像：

- 用户可以在设置页看到 Agent 记住了什么
- Agent 内部不再全量读取它
- 自动写入会按结构化记录重新渲染这个文件

在设置页手动保存 `MEMORY.md` 时，系统会按章节同步到 SQLite：镜像中带有 `mem_xxx` 前缀的既有记录会保留其可见置信度（例如 `[inferred]` 仍保持 inferred），新手写且没有镜像前缀的条目视为用户显式录入并写为 `confirmed`。如果某条 active 记录从镜像中消失，保存时会把该记录标记为 `deprecated`，因此删除行不会在同一次保存里复活。

## 与 AdGenieState / Observation 的关系

`agent_service.py::create_agent()` 现在给 LangGraph 显式声明了 `AdGenieState`（`user_goal` / `current_step` / `tool_history` / `observations` / `artifacts` / `error_state` / `retry_count` / `execution_status`），每次工具执行完成后由 `pre_model_hook=sync_observations`（`app/services/agent_state.py`）把 `ToolMessage` 标准化为 `Observation` 写回图内状态。完整设计见 `核心流程完整分析.md` §3.5。这一层和记忆系统是两个独立职责：

- **AdGenieState/Observation**：单轮对话执行期间的过程状态（本次调用了哪些工具、成不成功、产物是什么），只存在于 LangGraph 图的运行时内存里，对话结束（`[DONE]`）后不落盘，不参与检索。
- **记忆系统（本文档）**：跨对话持久化的结构化知识，落 SQLite，参与检索注入。

**已知的重复实现（尚未打通，记录以便后续合并）**：`upsert_session_digest()`（`memory_service.py:347`）里的 `_extract_outputs(tool_results)` 用来生成 Tier 2 摘要里的"最终产物"字段，但它的数据来源是 `chat.py` 在转发 SSE 事件时**独立重新解析**一遍 `tool_result` 文本（`chat.py:239-291`），和 `AdGenieState.artifacts` 是两条平行链路，产物提取/成败判定逻辑几乎是重复的。后续可以让 `upsert_session_digest` 直接读 `agent.get_state(config).values["artifacts"]`，替代 `chat.py` 里重新解析 SSE 文本的做法，避免两套判定规则跑偏。

**`write_memory` 工具本身也会被 Observation 化**：`write_memory`（`workspace_tools.py`）是注册进 Agent 的普通工具之一，失败时返回 `❌ ...` 前缀文本、成功时返回 `✅ ...` 前缀文本——这也是 `sync_observations` 的失败前缀识别列表里专门加了 `❌` 的原因（其他工具大多用 `Error:` 前缀或 JSON `{"error": ...}`）。也就是说，一次 `write_memory` 调用现在会产生两份独立记录：SQLite 里的 `memory_records`（记忆本身），和当轮 `AdGenieState.observations` 里的一条"这次写记忆操作成不成功"的过程记录。

## 关键代码

- `backend/app/services/memory_service.py`：SQLite 结构化记忆、会话摘要、检索、镜像导出
- `backend/app/services/workspace_service.py`：Tier 0 文件注入 + Tier 1/2 检索上下文拼接
- `backend/app/tools/workspace_tools.py`：`write_memory` 写入结构化 confirmed 记忆
- `backend/app/routers/chat.py`：流结束后更新会话摘要和 inferred 候选记忆
- `backend/app/services/agent_service.py`：传入当前 query/canvas_id，驱动按需检索；同时装配 `AdGenieState`/`pre_model_hook`
- `backend/app/services/agent_state.py`：单轮执行期的 `AdGenieState`/`Observation` 定义与标准化逻辑（与本文档的持久化记忆是两层）
