# AdGenie Agent 对话生成 完整分析

## 1. 概述

AdGenie 的核心流程是"对话式多模态内容生成"——用户输入自然语言 → Agent 自主推理 → 多步工具调用 → 媒体下载处理 → 画布自动插入 → 对话持久化。整个流程在 SSE 长连接内完成，用户实时看到 Agent 的思考过程和工具调用进度。与单纯的"调 API 返回结果"不同，AdGenie 的 Agent 具备多步推理能力——一次用户请求可能触发 5-15 次工具调用，形成完整的创作工具链。

**流程模式对比：**

| 模式 | 工具调用次数 | 典型耗时 | 示例 |
|------|------------|---------|------|
| 单步生成 | 1 | 5-15s | "生成一张图片" |
| 多步链式 | 3-6 | 30-90s | "生成图片 → 生成视频 → 拼接" |
| Skill 工作流 | 5-15 | 2-5min | 论文写作、播客制作 |
| 理解→创作 | 2-4 | 15-45s | "分析这张图的风格 → 生成类似风格" |

## 2. 数据加载机制

### 2.1 消息格式转换

用户消息从前端 JSON → LangChain 消息格式的转换发生在 `stream_processor.py:process_stream()` 中：

```python
for msg in messages:
    if msg.get("role") == "user":
        langchain_messages.append(HumanMessage(content=msg.get("content", "")))
    elif msg.get("role") == "assistant":
        langchain_messages.append(AIMessage(content=msg.get("content", "")))
```

消息历史直接注入 Agent 的 `astream()` 调用——不需要额外的 embedding 或向量化。历史长度由 LLM 的 context window（128K tokens）天然限制。当前没有实现消息历史的智能截断（如保留最近 N 轮 + 总结早期对话），这是后续优化的方向。

### 2.2 System Prompt 装配

每次 `create_agent()` 调用时，四大模块实时拼接：

1. **SYSTEM_PROMPT**（硬编码，~2500 tokens）——角色定义 + 行为规则
2. **工具列表**（动态生成，~1500 tokens）——`tool.name` + `tool.description`
3. **Skills 上下文**（实时扫描，6 个 Skill ~300 tokens）——Progressive Loading 元数据
4. **Workspace 上下文**（实时读取，500-1500 tokens）——有实质内容的身份文件

四模块按固定顺序拼接：角色 → 工具能力 → 领域专长 → 个性化记忆。这个顺序是有意设计的——先告诉 Agent"你是谁"，再"你能做什么"（工具），再"你有哪些专长"（Skill），最后"你记住了什么"（Workpace）。从通用到具体，从能力到记忆。

## 3. ReAct 循环逐轮详解

### Round 0: 接收用户消息

```
Agent 输入：
  System Prompt（完整）
  + 用户消息 "生成一个赛博朋克城市夜景，16:9，然后用这张图做首帧生成视频，最后拼接一段文字动画"

Agent 内部状态（AdGenieState，详见 §3.5）：
  messages = [HumanMessage("生成...")]   # system prompt 由动态 prompt 回调生成，不计入 messages
  user_goal = None                       # 首次 pre_model_hook 执行后从这条 HumanMessage 回填
  current_step = 0
  observations = []
  tool_history = []
  artifacts = []
  error_state = None
  retry_count = 0
  execution_status = None                # 尚未进入循环
```

### Round 1: 第一次推理

```
LLM 思考：
  "用户要求三个步骤：1.生成图片 2.生成视频（以图为首帧）3.视频拼接。
   先执行第一步——生成图片。16:9 尺寸、赛博朋克城市夜景主题。"

LLM 输出（tool_call）：
  {
    "name": "generate_volcano_image",
    "arguments": {"prompt": "赛博朋克城市夜景，霓虹灯光，雨夜，电影级画质，16:9", "size": "16:9"}
  }
```

**状态变化**：tools 节点被触发

### Round 1.5: 工具执行

```
generate_volcano_image_tool 执行：
  1. parse_size("16:9") → "2560x1440"
  2. POST /images/generations → API 返回 image_url
  3. download_and_save_image() → ICC→sRGB → JPEG quality=95
  4. return json.dumps({"image_url": "/storage/images/volcano_20250627_001.png"})

ToolMessage 追加到消息列表
```

**pre_model_hook（sync_observations）执行**（进入 Round 2 前）：

```
新 ToolMessage → Observation:
  {tool_name: "generate_volcano_image", tool_call_id: "call_1", success: true,
   structured_result: {"image_url": "/storage/images/volcano_20250627_001.png"},
   artifact_uri: "/storage/images/volcano_20250627_001.png",
   error_type: null, retryable: false, step: 1}

AdGenieState 更新：
  current_step = 1
  observations += [上面这条]
  tool_history += [{tool_call_id: "call_1", tool_name: "generate_volcano_image",
                     arguments: {...}, step: 1}]
  artifacts += [{tool_call_id: "call_1", tool_name: "generate_volcano_image",
                  uri: "/storage/images/volcano_20250627_001.png", step: 1}]
  execution_status = "running"
  error_state = null
```

### Round 2: 第二次推理

```
LLM 思考：
  "图片已生成，路径是 /storage/images/volcano_20250627_001.png。
   现在执行第二步——用这张图作为首帧生成视频。"

LLM 输出（tool_call）：
  {
    "name": "generate_volcano_video",
    "arguments": {
      "prompt": "城市夜景动态视频，霓虹闪烁，雨滴落下",
      "image_url": "/storage/images/volcano_20250627_001.png",
      "mode": "image"
    }
  }
```

**状态变化**：轮询视频任务（30-120s），完成后同样由 pre_model_hook 转换为一条新 Observation（current_step = 2）

### Round 2.5: 工具执行（异步）

```
generate_volcano_video_tool 执行：
  1. prepare_image_input() → 本地路径 → Base64 编码
  2. submit_task() → task_id
  3. poll_task():
     t=0s:   status="pending"
     t=5s:   status="processing"
     t=10s:  status="processing"
     ...
     t=35s:  status="succeeded", video_url
  4. download_and_save_video() → /storage/videos/volcano_video_001.mp4
```

### Round 3: 第三次推理

```
LLM 思考：
  "视频已生成。现在执行第三步——拼接。但用户说'拼接一段文字动画'，
   我需要先生成文字动画视频，然后拼接。不对，用户没有提供文字内容，
   我直接告知用户视频已生成，询问是否需要文字动画。"

LLM 输出（文本）：
  "好的！图片和视频都已生成。
   赛博朋克城市夜景图 → 16:9 横版
   动态夜景视频 → 基于首帧生成
   关于'文字动画拼接'——您想添加什么样的文字？比如标题、字幕还是特效文字？
   请提供文字内容和风格偏好，我继续帮您完成"
```

**状态变化**：无 tool_calls → 条件边路由到 END

### Round 4: 流结束

```
StreamProcessor 输出：
  1. delta 事件 × N（上述文本逐 token）
  2. [DONE] 事件

后端收尾：
  HistoryService.save_canvas() → chat_history.json
  所有工具结果中的媒体 URL 已通过 SSE 推送前端
```

### 3.5 State / Observation 闭环

`create_react_agent` 默认的 `AgentState` 只有 `messages`，工具执行结果只是消息列表里的一条 `ToolMessage`，模型能"看到"它，但代码里没有任何结构化的地方能读取"这次调用成功了没有 / 产物是什么 / 能不能重试"。`app/services/agent_state.py` 在不改变 `agent ⇄ tools` 循环结构本身的前提下，把这些信息显式建了模：

**接入方式**（两个 `create_react_agent` 官方扩展点，都在 `agent_service.py::create_agent()` 里）：

1. `state_schema=AdGenieState` —— 在内置 `messages`/`remaining_steps` 之外声明 `user_goal / current_step / tool_history / observations / artifacts / error_state / retry_count / execution_status`。
2. `pre_model_hook=sync_observations` —— 这个 hook 被插在图里 `tools → pre_model_hook → agent` 的位置（即每次工具执行完、下一次调用 LLM 之前），把本轮新增的 `ToolMessage` 标准化为 `Observation` 写回 State。
3. `prompt` 从静态字符串换成了 `build_prompt(state)` 回调 —— 每次调用模型前，把 `render_state_context(state)` 生成的 State 摘要（`current_step`/`execution_status`/`retry_count`/`error_state`/最近 5 条 Observation）拼进 system prompt，让模型每一轮都能读到最新状态，而不只是消息列表里那条原始 `ToolMessage` 文本。

**成功/失败判定**（`_normalize_observation`）：项目里的工具不靠抛异常表达失败，约定五花八门——有的返回 `json.dumps({"error": ...})`（无 "Error" 前缀），有的返回 `"Error: ..."` 文本，`write_memory` 甚至用 `❌`/`✅` emoji 前缀。判定顺序：

1. `ToolMessage.status == "error"` → 失败
2. 内容以 `Error/错误/Exception/Traceback/❌` 开头 → 失败
3. JSON 可解析且含 `error`/`success: false`/`status: "error"` 字段 → 失败
4. JSON 可解析且无错误字段 → 成功，尝试从 `image_url`/`video_url`/`model_url`/`local_path` 等已知字段抽取 `artifact_uri`
5. 非 JSON 且不带错误前缀 → 按成功文本处理

**去重与计数**：`tool_history`/`observations` 用 `operator.add` reducer 累加，`sync_observations` 每次靠已有 `observations[*].tool_call_id` 去重，避免同一条 `ToolMessage` 被重复写入；`current_step` 按本轮新增 Observation 数量递增（并行工具调用时也不会计错）。

**边界**：这一版只做 State-Action-Observation 闭环，不引入 DAG、Planner-Executor 或基于 Observation 的自动重试/重规划——`retry_count`/`error_state` 目前只是可观测数据，不驱动任何控制流变化。SSE 事件契约（`delta`/`tool_call`/`tool_result`/`skill_matched`）完全未改动，`stream_processor.py` 未被触碰。

## 4. 关键数据结构

### AdGenieState / Observation（`app/services/agent_state.py`）

```python
class Observation(TypedDict):
    tool_name: str
    tool_call_id: str
    success: bool
    structured_result: Any
    artifact_uri: Optional[str]
    error_type: Optional[str]
    retryable: bool
    step: int

class ToolHistoryEntry(TypedDict):
    tool_call_id: str
    tool_name: str
    arguments: Dict[str, Any]
    step: int

class ErrorState(TypedDict):
    tool_name: str
    tool_call_id: str
    error_type: str
    message: str
    retryable: bool

class AdGenieState(TypedDict):
    messages: Annotated[Sequence[BaseMessage], add_messages]
    remaining_steps: NotRequired[RemainingSteps]
    user_goal: NotRequired[Optional[str]]
    current_step: NotRequired[int]
    tool_history: NotRequired[Annotated[List[ToolHistoryEntry], operator.add]]
    observations: NotRequired[Annotated[List[Observation], operator.add]]
    artifacts: NotRequired[Annotated[List[Dict[str, Any]], operator.add]]
    error_state: NotRequired[Optional[ErrorState]]
    retry_count: NotRequired[int]
    execution_status: NotRequired[str]
```

`tool_history`/`observations`/`artifacts` 三个字段用 `operator.add` reducer 累加（LangGraph 的 `BinaryOperatorAggregate` channel），其余字段是覆盖写。详见 §3.5。

### StreamProcessor 内部状态

```python
class StreamProcessor:
    current_content: str = ""                              # 当前轮的助手回复文本
    text_buffer: str = ""                                  # 日志打印用累积缓冲区
    tool_call_args: Dict[str, Dict] = {}                   # 累积完成的工具参数 (tool_call_id → {arg: val})
    tool_call_names: Dict[str, str] = {}                   # 工具名称映射 (tool_call_id → tool_name)
    tool_call_args_buffer: Dict[str, str] = {}             # JSON 增量累积缓冲区 (tool_call_id → partial_json_str)
    skill_matched_emitted: Set[str] = set()                # 已发送过 skill_matched 的 tool_call_id 集合
    recursion_limit: int = 200                             # 从环境变量读取
```

**字段生命周期**：
- `tool_call_args_buffer` — 收到第一个 tool_call_chunks 时创建条目，收到 tool_result（工具执行完成）时删除条目
- `tool_call_args` — 与 buffer 同步创建/删除
- `skill_matched_emitted` — 整个对话周期内累积，不清理（同一个 Skill 不会匹配两次）

### Canvas 数据模型（前端）

```typescript
interface Canvas {
  id: string;                    // "canvas-1687900000000"
  name: string;                  // 用户可编辑的项目标题
  createdAt: string;             // ISO 时间戳
  messages: Message[];           // 完整对话历史
  data: {
    elements: ExcalidrawElement[];  // 画布上的所有元素
    appState: AppState;             // 视图状态（缩放、偏移、主题）
    files: Record<string, { dataURL: string }>;  // 媒体文件（Base64或URL）
  };
  images?: LegacyImage[];        // 旧版画布图片（迁移前兼容）
}
```

### ToolCall 状态机（前端）

```
创建: { status: "running", id, name, arguments }
  │
  ├── 收到 tool_result → { status: "completed", result, imageUrls?, videoUrls?, ... }
  │
  └── 超时/错误 → { status: "error", error }
```

## 5. 完整调用链

```
POST /api/chat
  │
  ├── chat.py: chat_endpoint()
  │   ├── 解析 ChatRequest (message, messages[], canvas_id)
  │   ├── 广播 user_message → WebSocket
  │   └── 调用 stream_and_save()
  │
  ├── agent_service.py: process_chat_stream()
  │   ├── 消息转换: JSON → LangChain (HumanMessage / AIMessage)
  │   ├── create_agent()
  │   │   ├── factory.create_llm() → ChatOpenAI
  │   │   ├── 注册 20 tools
  │   │   ├── skill_service.get_skills_context()
  │   │   ├── workspace_service.get_workspace_context()
  │   │   ├── prompt.get_full_prompt()
  │   │   └── create_react_agent(model, tools, prompt=build_prompt,
  │   │         state_schema=AdGenieState, pre_model_hook=sync_observations)
  │   │         # 图节点: agent ⇄ tools，tools → pre_model_hook → agent（详见 §3.5）
  │   └── StreamProcessor.process_stream(agent, messages)
  │
  ├── stream_processor.py: process_stream()
  │   ├── agent.astream({"messages": [...]}, stream_mode=["messages"])
  │   ├── for each chunk:
  │   │   ├── _handle_chunk(chunk)
  │   │   │   ├── tuple → _handle_message_chunk(data)
  │   │   │   ├── list → for msg: _handle_message_chunk(msg)
  │   │   │   └── direct → _handle_message_chunk(msg)
  │   │   │       ├── ToolMessage → yield tool_result 事件
  │   │   │       ├── AIMessageChunk + content → yield delta 事件
  │   │   │       └── AIMessageChunk + tool_calls/chunks → 参数累积 → yield tool_call 事件
  │   │   └── yield f"data: {json.dumps(event)}\n\n"
  │   └── yield "data: [DONE]\n\n"
  │
  ├── chat.py: stream_and_save() 内联
  │   ├── for each event: yield event + manager.broadcast(canvas_id, event)
  │   └── [DONE] 后: HistoryService.save_canvas(...)
  │
  └── 前端: ChatInterface.tsx SSE consumer
      ├── fetch POST /api/chat → ReadableStream
      ├── for each line (starts with "data: "):
      │   ├── delta → setMessages(prev => appendToLast(prev, content))
      │   ├── tool_call → setMessages(prev => addToolCall(prev, {id, name, args, status:"running"}))
      │   ├── tool_result → setMessages(prev => updateToolCall(prev, id, {result, status:"completed"}))
      │   │   └── extractMediaUrls(result) → pendingMediaRef.enqueue() or addToCanvas()
      │   └── skill_matched → showSkillBadge(skill_name)
      └── [DONE] → mark stream complete
```

## 6. 设计模式

| 模式 | 出现位置 | 说明 |
|------|---------|------|
| **工厂模式** | llm/factory.py | create_llm() 根据 provider 返回不同 Provider 实例 |
| **策略模式** | llm/base.py | VolcanoLLMProvider / SiliconFlowLLMProvider 实现相同接口，不同行为 |
| **观察者模式** | connection_manager.py | WebSocket 连接订阅 canvas_id，消息到达时广播通知 |
| **模板方法** | 所有 @tool 函数 | 统一结构：参数验证 → API 调用 → 结果处理 → JSON 返回 |
| **状态机** | StreamProcessor, ChatInterface | 工具调用 running → completed 状态流转 |
| **命令模式** | ExcalidrawCanvas useImperativeHandle | 父组件通过命令式 API 控制画布（addImage/addVideo/add3DModelPreview） |
| **渐进式加载** | skill_service.py | Skill 元数据常驻 + 内容按需加载 |

## 7. 故障排查指南

| 症状 | 可能原因 | 排查步骤 |
|------|---------|---------|
| Agent 不调用任何工具 | LLM 输出中无 tool_calls | 1.检查 LLM model 是否支持 function calling 2.检查 System Prompt 中的工具列表是否正确注入 |
| Agent 重复调用同一工具 | 工具返回后 Agent 不认为任务完成 | 1.检查工具返回的 JSON 是否包含明确的成功/失败指示 2.检查 recursion_limit 是否够用 3.查看该轮 Observation（`execution_status`/`retry_count`，见 §3.5）确认工具是否被判定为失败 |
| 工具返回 Error: API Key 未配置 | .env 中缺少对应 API Key | 1.检查 backend/.env 文件 2.确认环境变量名与代码中的 `os.getenv("KEY")` 一致 3.对应 Observation 的 `error_type` 应为 `config_error`（`retryable=false`），若不是说明分类规则需要补充新工具的失败文案约定 |
| 流式输出中断（前端停止接收） | SSE 连接超时或客户端断开 | 1.检查是否有 heartbeat 事件保持连接 2.检查视频生成时 SSE 是否在 600s 超时前断开 |
| 画布元素重复插入 | pendingMediaRef 和直接插入的竞争条件 | 1.检查 drainPendingMedia() 的去重逻辑 2.检查 computeNextPosition() 的坐标计算 |
